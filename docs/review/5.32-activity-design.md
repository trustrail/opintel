# 5.32 Activity: implementation decisions for review

## Historical facts and filter meaning

Keep the record route as a permalink for an evidence id, Dashboard links,
exports and bookmarks. The inline expansion and route share one detail reader;
the list's disclosure does not navigate or fetch detail while closed.

Approved filter: label it **Answer treated**, counting completed
answers with recorded tokenized, masked or aggregate-only deliveries. It does
not classify planned reads, omitted fields, refused requests or incomplete
requests as sensitive answers. Rollups use retained delivery treatment counts
and identify the loss of element detail. A clearer name avoids claiming a
classification of customer sensitivity that no stored fact establishes.

Daily summaries count the complete matching scope, not just loaded pages, in
UTC calendar days, labelled once **Days grouped in UTC**. Absolute timestamps
keep the reader's preferred zone. Counts, day strips and pagination use the
same filter definition and tenant scope. Object/element search reads historical
metadata only, never hidden arguments or today's catalogue.

The existing source-plan snapshot records object addresses and planned column
treatments. Element delivery rows separately record released/aggregated elements
and omissions. It does not record an operation classification: two referenced
objects do not establish a join, and an aggregate-only treatment does not prove
COUNT. New operation labels must come from structured inspection metadata,
without literals or aliases, recorded as evidence, never telemetry. Existing
records without those facts use an honest object-count label; sampled/retained
records do not reconstruct absent plans from SQL or current policy.

Refusal explanations project known-safe structured cause fields and names;
they do not return arbitrary stage JSON or an unchecked historical message.
An unsatisfiable-join detail links to the existing candidate's element pair and
pool scope. No new suggestion decision or automatic domain change is introduced.

Treatment summaries show actual deliveries. Star omissions are separately
labelled; explicitly named withheld fields refuse by name. Planned objects must
not be presented as delivered elements, or unrelated withheld fields added from
the object's full snapshot. Incomplete says **No answer was recorded**, with no
claim about whether a response reached the agent.

Outcome badges alone carry row colour. Treatment marks use neutral ink here,
with accessible names and visible count labels; unlike the Entitlements colour
legend, Activity's design intentionally gives colour to outcome only. Each
treatment summary badge is its own marked item, separate from the request's
state mark, so placement checks remain meaningful and unchanged. No query kind
mark in the uniform list, or screen-name mark in a heading/empty state.

Targets: desktop closed row 42px where its two identity lines fit, primary label
13.5px/560, secondary/actor labels 12px, day strip at least 32px, paired detail
columns 1.25:1 with 16px gap. Long names and full absolute/relative timestamps
may increase row height; narrow layouts preserve content rather than hide it.
Variable-height expansion and day rows need measured virtualizer offsets, with
only the visible bounded window and open visible detail mounted.

## Row and strip reader review

The initial day strip incorrectly normalised counts to approximately 18 dots;
it did not render one mark per request. Exact per-outcome counts already exist
in the complete-day summary. The correction must preserve those counts, with
no proportional sampling. The earlier canvas proposal was not applied. Reader review reiterated the
exact-count requirement. The correction uses SVG repeated 6px marks at 9px
pitch: each outcome band is exactly its request count wide, without a DOM
node per request or proportional sampling. The existing strip scrolls
horizontally when it exceeds the available width.

Row identity now uses the pool name from the project pool read model, never its
authentication-key prefix. The pool is omitted only when the known single
project pool matches the recorded pool id. Missing/deleted names are explicitly
unavailable rather than guessed from a key. The agent column is widened from
130px to 210px, with its complete identifier retained in the title.

A refused row's “Planned to read 2 objects” is the approved historical
object-reference fallback, not an attempted-operation classifier. 5.32a is
required to establish the actual operation; no join is inferred from two objects.

The focused row check passed at 1440px: `engine-test-harness` measures
148.80px and fits without truncation. Single-pool omission and two-pool
name display both passed; no key prefix remains in the row. Axe and
partial conformance (1/53 routes) report zero findings. No visual project
or baseline regeneration ran.

Follow-up row review removes the synthetic-source annotation from the pool
column. The pool line contains only the pool name. The primary label and object
list each remain a single line, with ellipsis and full text in their titles.
A refused operation keeps the historical object-count fallback; its wrapping
